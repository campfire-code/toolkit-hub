# 打磨子任务说明（自研桌面工具）

你负责打磨**一个**自研桌面工具：界面要有自己的样子，所有文字只用中文。工具的功能和数据处理逻辑**不改**，测试必须照样全部通过。

汇总仓库：`/Users/wumin/Project/small-project`。工具目录：`tools/<slug>`，它是独立的 git 仓库。

## 背景

- 用户反馈：所有工具都是同一个模板套出来的，看起来一模一样，包括侧栏、拖放区、列表、参数面板。
- 用户要求：产品里只能有中文。

## 要做的事

1. **读懂工具。**
   - 读 `README.md`、`src/tool/index.ts(x)`、`src/tool/` 下的界面文件、`catalog/copy/<编号>.json`（上架文案）。
   - 用 `node scripts/shot.mjs <编号>` 截一张现状图，用 Read 看。
2. **定专属外观。**
   - 主色：把 `catalog/style.json` 里这个编号的 `accent` 写进 `tool.json` 的 `ui.accent`。外壳会用它覆盖主色。
   - 布局：`ui.layout` 可以按工具用途改选 a～f（a 侧栏、b 紧凑侧栏表格、c 暖色卡片、d 左列表右预览、e 居中单栏、f 顶部标签）。选最能突出这个工具核心结果的布局。
   - **同分类不撞版式：**先运行 `node scripts/layout-map.mjs <分类>`，看同分类工具已用的布局，尽量选用得少的。批量型工具不要再选「a 侧栏 + 行列表」，已经有太多。外壳已更新：a、c、d、e、f 都会显示自定义 `Empty` 和 `ResultBody`（d 显示在右侧预览区），只有 b（表格）不显示 `ResultBody`。
   - **批量型工具要改得大胆：**只在列表行里加一行小字不够。结果展示要成为画面主角，例如：
     - 图片类：大缩略图做前后对比。
     - 文字识别类：原图和识别文字左右对照。
     - 表格类：关键数字用大字显示。
   - 参考样品：e12（抖店改价）的「核对条 + 旧值 → 新值」就是合格的程度；o02（PDF 百宝箱）只在行里加小图示，改动偏保守，不要照它做。
3. **重做主体界面。**围绕这个工具最核心的那一个结果来设计，让人一眼看出它是干什么的。
   - **批量 / 生成型工具**（`mode: 'batch' | 'generate'`）用外壳提供的两个接口：
     - `Empty`：还没添加文件时的空状态。不要只放一个拖放框，要讲清楚这个工具把什么变成什么。可以画一个示意，例如「几份 PDF → 合并成一份」的图示，用 SVG 或 CSS 画，不要 emoji。
     - `ResultBody`：单条结果的展示。用最能说明结果的形式，例如前后对比、识别出的文字、价格从多少改到多少、压缩省了多少。
     - 两个接口的类型见 `src/kit/types.ts`。
   - **自定义型工具**（`mode: 'custom'`）：直接重做 `Main` 和 `src/tool/tool.css`。
     - 要求：信息层级清楚，有一个视觉焦点。
     - 不要和其他工具一样都是「白卡片堆叠」。
     - 可以用分栏、时间线、看板、数据大字、对比视图等形式，选和业务匹配的。
   - 设计规则：
     - 对比度达到 4.5:1。
     - 可点击区域不小于 32px。
     - 字号层级清楚，正文不小于 13px。
     - 只用 lucide-react 图标，不用 emoji 当图标。
     - 亮色和暗色都要好看。
     - 动效 150～250ms。
4. **只用中文。**
   - 按 `docs/术语表.md` 把界面上所有给用户看的文字改成中文：按钮、标签、提示、报错、占位、示例数据都算。
   - 示例 / 演示数据用真实感的中文：店名、商品、人名、群名。不要用 Sample、Test、demo。
   - 用 `node scripts/check-zh.mjs <编号> --list` 检查，结果必须是 0 处。
   - 如果确实需要保留某个词（平台后台的官方字段名），先确认它属于术语表「保留原文」的类别，再加进术语表，并在交回报告里说明。
5. **重写上架文案** `catalog/copy/<编号>.json`。
   - 保持原有字段，另外加 `scene: { "title": "...", "body": "..." }`：写一个具体的使用场景，一两句话，比如谁、在什么时候、用它省了什么事。
   - `slogan` 和 `features` 要写出这个工具自己的特点，不要套话。
   - 只写工具真实具备的功能，以代码为准，不编造。
   - 全部中文，标准同上。
6. **验证。**全部要通过：
   - `pnpm exec tsc --noEmit`
   - `pnpm test`
   - `pnpm build`
   - `node scripts/shot.mjs <编号>`：重截 `docs/screenshot.png`，用 Read 看图，不满意就继续改。开发预览已应用 `ui.accent`。
   - 暗色也要检查：开发预览地址加 `?state=running&mode=dark`，可以临时改 `shot.mjs` 的参数，或者自己用 playwright-core 截一张，看完删掉，不要提交。
   - 截图里不能有英文，不能有报错。
7. **升版本并提交。**
   - 版本号把小版本加一（例如 0.1.0 → 0.2.0），要改 `tool.json`、`package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`。
   - `CHANGELOG.md` 加一节，用中文写这次改了什么。
   - 用 `git -c user.name=wuniba1997 -c user.email=wuniba1997@gmail.com commit` 提交，结尾加一行 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`。
   - **不推送、不打标签、不发版**，发版由总控统一做。

## 不许做

- 不许为了让中文检查归零而删掉或改动用来**识别数据**的英文（导入表头的别名、接口字段、文件内部名称）。这类字符串在上一行加注释 `// check-zh: 忽略（原因）`，检查脚本会跳过。

- 不改 `src/kit/`。它是所有工具共用的，改了会被同步覆盖。如果外壳缺你需要的能力，在交回报告里写清楚。
- 不改功能逻辑和数据格式；不删测试。
- 不动汇总仓库里别的工具，也不动 `catalog/style.json`。
- 不写明文密钥；不联网安装新依赖。确实需要新依赖的话，先在报告里说明原因，不要自己装。

## 交回报告（中文，简短）

- 改了什么：外观、布局、空状态和结果展示、中文化处数。
- 验证结果：类型检查、测试数、构建、中文检查、截图路径。
- 提交号。
- 遗留问题。
